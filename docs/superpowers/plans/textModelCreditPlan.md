# 文本模型积分规则优化计划

**目标：** 保留“1元人民币＝10积分”，将文本模型的字符报价与统一 token 扣费，改为覆盖API采购及人工运营服务预算的分项token计费。以用户确认的“旧实扣总额约1/5”为本版商业目标，使用户能逐笔复算。

**架构：** 复用现有价格版本、生成任务、个人钱包、账本及数据库事务。文本价格新增分项费率，金额改为六位小数定点运算；媒体模型继续使用原有业务定价，只适配共同的钱包金额类型。

**技术栈：** Bun、TypeScript、Express、Drizzle、MySQL、Vue；金额使用标准库 BigInt，不新增金额计算依赖。

**依据：** 用户要求先提交计划；2026-10-14已核对的公开API计费资料、136笔任务审计及用户提供的两笔供应商成本截图。用户已批准实施；本版已在隔离分支 codex/textBilling 完成代码及本地验证，生产迁移和价格发布尚未执行。

**当前试用规则：** 按用户最新确认，新发布文本价目直接填写四项积分／百万 token，不再配置采购价或服务加价。GPT四项为75.60／7.56／94.50／604.80；百炼DeepSeek和千问各为GPT的50%，Claude Opus 5为150%。以下采购价与加价章节描述先前V2方案；最新接口、界面及验证以文末V3调整记录为准。136笔GPT历史usage重算仍为241.982750积分，页面显示241.98。

## 三、建议计费规则

### 1. 按供应商和模型分别定价

文本的计费单位统一为“每百万token”。每个供应商、真实上游模型及服务档位配置以下费率：

- 非缓存输入 `input`。
- 缓存读取 `cacheRead`。
- 缓存写入 `cacheWrite`，仅供应商确实计费时配置。
- 输出 `output`，包含已计入输出的思考token。

有不同缓存保留时长的模型增加对应写入档位；`cacheWrite1h` 是总写入量的子集，不能再重复加一次。模型不支持的计费项用明确的“不适用”表示，不能把未知费率填成0。

优先使用用户实际渠道的完整人民币费率，包括模型映射、供应商倍率、服务档位、币种和折扣。官方公开价格用作参考，不直接覆盖中转供应商实际采购费率。促销到期、长上下文或不同服务档位改变费率时发布新版本；没有对应价格的档位在请求前拒绝，不默默套基础价。

建议管理员按“采购价＋人工运营服务预算”生成零售费率预览。本版gpt-5.6-sol采用2.16倍采购基费，即加价116%；这是按旧收费约1/5校准的商业方案，不是行业统一倍率，其他模型需单独定价。汇率、供应商倍率、服务加价比例及最终零售费率锁进价格版本，不在结算时读取实时汇率。

### 2. 统一计算公式

```text
应计积分 = (
  非缓存输入token × 输入积分单价
  + 缓存读取token × 缓存读取积分单价
  + 缓存写入token × 对应写入积分单价
  + 输出token × 输出积分单价
) / 1,000,000

零售积分单价 = 采购人民币单价 × 10 × (1 + 人工运营服务加价比例)
本版人工运营服务加价比例 = 116%，即总采购倍率2.16
```

单价单位均为每百万token。实际扣费使用锁定的零售单价，不使用SDK里的 `usage.cost`：当前运行时将这些cost字段配置为0，并不代表供应商免费。

取消“最低一整积分”和“每一万token先向上取一单位”。分类金额先精确相加，最后仅对该任务总额四舍五入一次，保留6位小数。真实0用量或者明确的免费价格扣0积分。

内部 `pi-ai` 的 `usage.input` 已经是非缓存输入，不再次减缓存。供应商原始usage只在进入该标准格式时归一化一次；`reasoning` 已包含在 `output` 时不重复收费；`totalTokens` 仅用于校验和展示。

### 3. 金额精度

钱包余额、冻结、账本金额、任务报价/实扣及划转金额统一为 `DECIMAL(26,6)`，数据库驱动保留十进制字符串。服务端内部转换为BigInt微积分：

```ts
type CreditAmount = string; // 对外固定6位小数，例如 "0.780286"

const microCreditsPerCredit = 1_000_000n;
const tokensPerMillion = 1_000_000n;

// 每项费率先转换为“每百万token对应的微积分”。
// numerator = 各分类 token × 对应 rateMicro 的精确整数总和。
const chargedMicroCredits = (numerator + tokensPerMillion / 2n) / tokensPerMillion;
```

只在总额处舍入；分项详情同时保留token、原始单价和未舍入的整数分子，避免分项显示舍入造成总额无法解释。

历史10000积分等值变为 `10000.000000`，不能把数据库余额乘百万。管理员发放、调整和团队划转暂时保留现有整数输入，转换到统一金额类型后运算；本次不扩展小数划转交互。

现有钱包 `balance <= 9007199254740991` 的限制暂时保留，避免顺便扩大余额额度；余额非负、冻结不超过余额、划转为正的数据库约束继续有效。

### 4. 报价、冻结和授权上限

报价覆盖最终实际请求：系统提示、消息历史、工具定义、工具结果、追加的文本/图片/视频参考，以及最终生效的输出和思考预算。不能再只数 `context.messages` 的JSON字符。

输入使用模型支持的token计数能力；没有现成计数接口/分词器时使用明确标记的保守估算。纯文本与工具文本的初始回退可按UTF-8字节数估算token，再计入协议开销；该结果只用于冻结，不成为最终usage。图片、视频等附件按供应商公开规则估算，缺少该模型附件计量规则时使用模型上下文上限作为保守输入预算并标记估算原因，不能把base64长度直接算成文本token。

输出预算来自实际传给上游的参数及适配器规则，并受模型输出与上下文上限限制。普通生成复用当前配置的输出上限，不擅自降低内容长度；Agent两个运行时入口使用其最终生效参数。思考预算根据协议判断是否包含在输出上限内，不能盲目相加。

预留不预先假定缓存命中；按所有适用输入类别（普通输入、缓存读取、缓存写入及时长档位）的最高费率及输出预算估算。长上下文档位可能跨阈值时按较高适用档预留。冻结金额向上保留6位小数。

建议把报价明确展示为“本次最高授权积分”，完成后只扣真实usage计算的金额并释放余量。若真实应计超过授权：实扣不超过授权，差额记录为平台承担；同时保存完整应计金额，不能像现在一样截断后冒充真实计算结果。该规则的代价是平台承担估算误差，因此要记录差额以便校准估算器。

### 5. 失败、取消与usage缺失

- 请求未发起，或供应商明确无计费用量：释放预留，扣0积分。
- 取消、断流或失败但取得真实usage：按实际发生用量结算，记录停止原因。
- 已发起上游但拿不到可核验usage：释放预留，实扣0，记录 `usageMissing` 及可取得的供应商requestId、响应证据；不能按报价全扣或伪造0用量。
- 迟到的计量数据用于供应商成本核对，不在已释放后自动补扣用户。成本未知时不能写成“供应商成本为0”。
- 返回内容成功与计费证据缺失分开处理，不因缺usage把已生成内容改为失败、诱发再次生成。

本次复用现有恢复机制与任务快照记录这一政策，不新增待核对冻结期、后台对账服务或管理员手工补扣功能。服务重启释放时保留已开始上游调用及计量未知的证据。
