# RunningHub Agent、Skill、无限画布与短剧项目调研

**日期：** 2026-11-15（北京时间）<br>
**范围：** 仅整理公开可访问的 RunningHub 产品入口和官方公开文章。官方资料没有披露的内部实现均标为未知，不从界面推导其私有 Agent 架构。

## 结论先行

RunningHub 公开呈现的是一组互补的创作入口，并非一个统一的 Agent 形态：

| 产品入口 | 公开可确认的工作方式PXAPP | 更适合的任务 |
| --- | --- | --- |
| 快捷创作中的 Agent | 用户选择 Skill 或 AUTO，描述最终目标；Agent 生成后可继续对话修改。官方介绍把 Agent 概括为围绕目标理解任务、判断/规划、调用系统提供的工具或能力、根据结果继续调整。 | 用户知道想要什么，但不想手工拆解全部操作步骤。 |
| AI 应用 | 封装好的具体创作工具或任务入口。 | 目标明确、希望直接使用现成能力。 |
| ComfyUI 工作流 | 用户控制更细的节点流程。 | 需要可复用、可调参数的确定性流程。 |
| RHTV 无限画布 | 用户把素材、文字、图片生成和视频生成等节点放在同一画布，连接输入输出并保留分支。 | 多素材、反复尝试、需要可见依赖关系的视觉创作。 |
| RH STORY | 独立的短剧项目创作入口，公开教程展示“有想法/有剧本”入口以及剧本、美术、分镜、短片生成阶段；项目围绕角色、场景、道具和镜头保持连续性。 | 有分集、角色和镜头关系的连续短剧生产。 |
| API | 模型、AI 应用、工作流、LLM 等 API。 | 外部产品或自动化集成。 |

官方 Agent 文章建议首次用户从 AUTO 开始；并未说明 AUTO 内部采用哪些模型、Agent 数量、记忆系统、Skill 文件格式或工具编排实现。公开文案中的“Skill”可能是可选择的创作路径/能力入口，**不能据此断定它等同于本系统的 `SKILL.md` 文件包**。

## Agent 与 Skill

RunningHub 官方教程描述的用户过程是：进入快捷创作 → 点击 Agent → 选择 Skill 或 AUTO → 描述目标和限制 → 生成初稿 → 围绕结果多轮提出修改。AUTO 的公开作用是根据创作需求选择合适路径，降低用户预先理解复杂工作流的成本。文章强调用户无需一次写出完美 Prompt，应先说清目标、素材、受众、风格和不可改变内容，再按结果继续调整。

这说明产品体验把“任务目标”置于 Skill 之前：普通用户先表达要完成什么，系统再协助选择路径。固定 Skill 适合已知任务；AUTO 适合未掌握内部流程的用户。公开文章没有展示“不使用 Skill”这一第三选项是否存在，因此不能把我们当前三种模式说成 RunningHub 的原样设计。

公开资料未确认：

- Skill 是系统提示词、节点工作流、工具集合还是它们的封装组合。
- AUTO 是否会根据项目状态、画布内容、模型能力、历史偏好排序。
- Agent 是否能在无限画布中自动创建或修改节点。
- RH STORY 是否调用与快捷创作相同的 Agent/Skill 系统。
- Skill 是否存在市场、版本治理、权限声明或用户安装范围。

## 无限画布

官方产品矩阵将 RHTV 标为“无限画布”，并将它与快捷创作、AI 应用、ComfyUI 工作流和 RH STORY 并列。公开画布教程展示一种显式的可视化数据流：先上传人物参考图，分别生成多套服装图，再准备统一场景和分镜文字，最后把人物图、场景图、服装图、分镜文本接入视频生成节点。节点之间的连接表达素材依赖，生成结果可以作为后续节点输入；多个分支可以共享一份参考素材。

教程还强调明确参考图顺序、控制同一片段中的对象数量、固定场景和人物，并通过局部重新生成迭代结果。由此可以确认无限画布的用户心智是“看得见、能连接、能分支的工作流”，而不是纯聊天。公开资料没有证明 Agent 自动操控画布，因此设计系统时应把 Agent 提案和用户可见的画布结构分开，不把自动改图当成已被 RunningHub 验证的模式。

## RH STORY 短剧生产项目

官方 RH STORY 教程展示了以项目阶段组织生产的流程：

1. 入口区分“有想法”和“有剧本”，让用户从创意或既有剧本接入。
2. 剧本阶段明确故事类型、角色、人物目标、核心冲突、分集节奏和结尾钩子。
3. 美术设定阶段把人物、服装、场景、道具和视觉风格整理为后续镜头可复用的素材。
4. 分镜阶段把剧情拆成镜头，明确景别、动作、运镜、情绪和时长。
5. 短片生成阶段按剧集/镜头查看描述、关联角色场景道具和媒体素材，并预览已生成结果。
6. 发现连续性问题时，教程建议返回美术设定或分镜修订；单个镜头偏差可只调整对应镜头，而不要求重做整部作品。

RH STORY 和无限画布在 RunningHub 的公开产品矩阵中是不同入口：前者侧重短剧对象和阶段，后者侧重任意节点与素材连接。公开文章没有说明两个入口是否共享同一套持久化数据模型，也没有披露内部审核/版本/事务实现。

## 对当前系统的设计启示

- Agent 输入体验应先让用户描述任务，再给 AUTO 和固定 Skill；固定选择要从同一菜单直接进入 Skill 浏览，不能出现无法操作的“固定”状态。
- AUTO 推荐理由要说清命中内容；不匹配时回退普通对话。选择 Skill 不应自动授予工具权限或触发媒体生成。
- 无限画布继续作为用户可见的节点图和素材流。未来如提供 Agent 帮搭流程，应先生成可编辑的节点提案，再由用户审阅；运行生成仍走报价、预算、幂等和明确授权。
- 生产项目使用项目、剧集、资产、场景、镜头和生成任务作为权威状态。Agent/Skill 产物应落入可审阅草稿，再通过事务写回对应对象，避免另造只存在于聊天里的项目状态。
- 跨阶段衔接应以版本引用和对象 ID 传递：剧本版本 → 资产版本 → 分镜修订 → 生成任务/候选。上游变化应标记下游待复核，而不是自动覆盖。
- 当前阶段四的“已有剧本 → storyboardTeam → 待审草稿 → 原子确认写入镜头”与公开 RH STORY 的项目阶段思路一致；这属于架构借鉴，不代表 RunningHub 内部就是同样实现。
